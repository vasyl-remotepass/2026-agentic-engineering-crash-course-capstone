# Рев'ю `tt.py`

Тести зелені (`Ran 14 tests … OK`), але я знайшов 4 проблеми. Найсерйозніша: шлях, де `~/.tt.json` перезаписується обрізаним невалідним JSON. Кожну знахідку відтворено з `TT_FILE` у `tempfile.mkdtemp()`. `tt.py` я не редагував.

Номери рядків нижче взято з сирого файлу (`grep -n`). Мій `cat` іде через rtk, а він стискає порожні рядки, тому в його виводі номери зсуваються.

## Знахідка 1 — `save()` спочатку обнуляє файл, потім пише: збій посередині лишає обрізаний невалідний JSON
- **Серйозність:** висока
- **Де:** tt.py:27–29 (`open(path(), "w")` + `json.dump`)
- **Відтворення:** журнал на 200 записів (15903 байти), запис обмежено через `ulimit -f 8`, потім `python3 tt.py start new`:
  - вийшло: `OSError: [Errno 27] File too large` (traceback), файл обрізано до 4096 байт і він закінчується на `"task": "t3`;
  - далі `tt status` → `error: corrupted data file … Unterminated string`, тобто весь журнал втрачено;
  - очікувалось: старий файл лишається цілим, `error: …`, код 1.
  - Так само спрацює заповнений диск, Ctrl-C або вбитий процес під час `json.dump`. Spec прямо каже: «Втрата даних гірша за незручність».
- **Чому тести не зловили:** тест `test_corrupted_file_is_error_and_not_overwritten` перевіряє лише, що *вже пошкоджений* файл не перезаписується. Збою *під час* запису він не моделює. Типове виправлення: писати в тимчасовий файл у тій самій теці, потім `os.replace`.

## Знахідка 2 — валідний JSON неправильної форми дає traceback замість `error:`
- **Серйозність:** середня
- **Де:** tt.py:17–24. `except (ValueError, KeyError, TypeError)` захищає лише `json.load(f)["entries"]`. Самі записи вже не перевіряються, і вони падають далі: у `running()` (:38), у `cmd_start` (:48) і в `cmd_report` (:84–86).
- **Відтворення:** записати файл, запустити `python3 tt.py <cmd>`:

  | вміст файлу | команда | вийшло |
  |---|---|---|
  | `{"entries": 5}` / `null` | start/stop/status/report | `TypeError: 'int' object is not iterable` |
  | `{"entries": {}}` | start | `AttributeError: 'dict' object has no attribute 'append'` |
  | `{"entries": "abc"}` | start | `TypeError: string indices must be integers` |
  | `{"entries": [{"task":"x"}]}` | stop/status → report | `KeyError: 'end'` → `KeyError: 'start'` |
  | `{"entries": [1]}` | будь-яка | `TypeError: 'int' object is not subscriptable` |
  | `start: "garbage"` | report | `ValueError: Invalid isoformat string` |
  | `start: "…+03:00"` (з таймзоною) | stop/report | `TypeError: can't subtract offset-naive and offset-aware` |

  Очікувалось: `error: corrupted data file …`, код 1 (правило 7). Код виходу тут і так 1, бо Python падає з 1, але виводиться traceback, а не повідомлення.
  - Дані не псуються: усі ці падіння стаються до `save()`. Виняток — знахідка 3.
- **Чому тести не зловили:** єдиний тест на пошкодження використовує синтаксично невалідний `{not json`. Структура не перевіряється ніде.

## Знахідка 3 — `stop` спочатку зберігає, потім падає: зміна записана, а користувач бачить traceback
- **Серйозність:** середня
- **Де:** tt.py:59–60 (`save(entries)` стоїть перед `datetime.fromisoformat(cur['start'])`)
- **Відтворення:** `{"entries":[{"task":"x","start":"oops","end":null}]}` → `python3 tt.py stop`:
  - вийшло: `ValueError: Invalid isoformat string: 'oops'`, rc=1, але `end` у файл уже записано, і `tt status` після цього каже `nothing running`, rc=0;
  - очікувалось: або помилка без змін (як у правилі 1, «нічого не змінюється»), або успіх. Не обидва одразу.
  - Так само з `start`, що має таймзону.
- **Чому тести не зловили:** stop тестується лише на записі, який створив сам `tt start`, тож `start` там завжди валідний.

## Знахідка 4 — від'ємна тривалість форматується як нісенітниця
- **Серйозність:** низька
- **Де:** tt.py:32–34 (`fmt`). `int(...) // 60` округлює до мінус нескінченності, а `divmod` з від'ємним числом дає `(-1, 59)`.
- **Відтворення:**
  - `python3 -c 'import tt;from datetime import timedelta;print(tt.fmt(timedelta(seconds=-30)))'` → `-1h 59m`;
  - запис зі `start` у майбутньому, потім `tt status` → `▶ docs — -633328h 17m`;
  - очікувалось: правило 6 знає лише `Xh YYm` / `Ym` / `0m`, тож щонайменше `0m` або помилка.
  - На практиці трапляється, коли годинник переводять назад: NTP, ручне налаштування. Пояси spec свідомо виключає, але переведення годинника туди не входить.
- **Чому тести не зловили:** `FormatTest` перевіряє лише значення ≥ 0.

## Знахідка 5 (дрібна) — помилки ОС дають traceback
- **Серйозність:** низька
- **Де:** tt.py:19 і :28
- **Відтворення:**
  - `TT_FILE=<тека> python3 tt.py status` → `IsADirectoryError` (traceback);
  - файл з `chmod 444` → `python3 tt.py start x` → `PermissionError` (traceback);
  - очікувалось: `error: …`, код 1 (правило 7).
- **Чому тести не зловили:** таких тестів немає. `load()` ловить лише `FileNotFoundError`.

## Перевірено, проблем немає
- `python3 -m unittest`: 14 тестів, OK.
- `start`: аргументи склеюються через пробіл, а краї обрізаються (`"  write   spec "` → `write   spec`). Порожня назва і назва з самих пробілів дають помилку, файл не створюється.
- Правило 1: `start`, коли таймер іде, дає помилку з назвою поточної задачі, файл не змінюється.
- Правило 2: `stop` без запущеного таймера дає помилку і код 1.
- `status`: показує запущений таймер / `nothing running`. Немає файлу → порожній журнал.
- `report`:
  - сортування від більшого до меншого і `total`;
  - запущений таймер рахується до `now` (правило 4);
  - запис після півночі належить дню старту (правило 5);
  - порожній день дає `total  0m`.
- `--date`: `2026-02-30`, `20261002` і `2026-W40-5` дають помилку. `--date` без значення або зайвий аргумент дають `usage`, код 1.
- Невалідний JSON, порожній файл, `[]` на верхньому рівні і не-UTF-8 байти (`UnicodeDecodeError` — підклас `ValueError`) дають `error: corrupted data file`, файл не перезаписується.
- `tt` без аргументів і невідома команда: usage у stderr, код 1.
- `datetime.now()` викликається лише в `__main__`, логіка отримує час параметром `now`. Код використовує лише stdlib.
- Кирилиця в назві задачі: `json.dump` з типовим `ensure_ascii=True` пише чистий ASCII, тож кодування локалі ні на що не впливає.
- Невідомі ключі верхнього рівня (наприклад `"meta"`) при `save` мовчки зникають. Spec визначає лише `entries`, тож порушенням spec це не є. Просто майте на увазі, якщо формат колись розширюватиметься.

`★ Insight ─────────────────────────────────────`
- Знахідки 1 і 3 мають спільну причину: ефект, який не можна скасувати (`open("w")` / `save`), стоїть *раніше* за код, що ще може впасти. Безпечний порядок такий: спершу все порахувати й перевірити, потім атомарно записати (tmp + `os.replace`).
- `except (ValueError, KeyError, TypeError)` у `load()` виглядає надійно, але покриває лише один вираз. Пошкоджені дані проходять далі й падають у місцях, які ніхто не обгортав. Перевірку схеми варто робити в тому ж місці, де читається файл.
- Тест `test_corrupted_file_is_error_and_not_overwritten` пропустив знахідку 1, бо перевіряє один вхід (невалідний файл), а не один інваріант (файл на диску завжди валідний).
